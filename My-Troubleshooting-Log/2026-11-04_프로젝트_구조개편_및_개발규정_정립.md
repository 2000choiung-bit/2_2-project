# 📝 [Troubleshooting] 멀티 파트 연동 병목 해결을 위한 프로젝트 구조 개편 및 개발 규정 정립

## 1. 개요 (Overview)

* **작업 내용**: 프론트엔드, 백엔드, DB 파트 간의 파일 엉킴 및 브랜치 충돌을 해결하기 위한 Monorepo 방식의 폴더 재구조화, AI/팀원 공통 개발 규정(`AI_RULES.md`) 작성 및 주차별 마일스톤(`TASKS.md`) 설계
* **관련 기술**: Git/GitHub, Monorepo Architecture, Spring Boot 3.x, React (Vite), MySQL, Markdown

---

## 2. 발생한 문제 및 해결 과정 (Trouble Shooting)

🔴 **문제 1: 최상위 루트 폴더 내 백엔드/프론트엔드/DB 파일 엉킴 및 Git 브랜치 충돌**

* **원인**: 각 파트(백엔드, 프론트엔드, DB) 담당자가 작업 브랜치를 main으로 통합하는 과정에서 프로젝트 최상위 루트에 `src`, `node_modules`, `gradle` 및 개별 `.js`, `.sql` 파일들이 무분별하게 덮어씌워지고 중복 생성됨. 이로 인해 브랜치 병합(Merge) 시 지속적인 충돌(Conflict)이 발생하여 작업 병목 유발.
* **해결**: 프로젝트 최상위 구조를 `backend/`, `frontend/`, `database/` 3개의 완전히 독립된 폴더로 분리(Monorepo 구조 도입). 루트에 존재하던 잔여 찌꺼기 파일 및 중복 폴더를 전면 정돈하고, 각 브랜치(`feature/backend-fit`, `feature/fe-ui`, `feature/db`)의 작업물을 해당 독립 폴더 내부로 재배치한 후 `main` 브랜치에 정립.
* **느낀점**: 프로젝트 초기에 폴더 격리와 권한/영역 분리가 명확하지 않으면 연동 시점에 상상 이상으로 큰 파일 꼬임과 생산성 저하가 발생한다는 것을 깨달았다. 백엔드 개발자로서 단순히 서버 로직만 짜는 것이 아니라 전체 프로젝트 구조(Directory Structure)를 깔끔하게 정돈하고 협업 파이프라인을 구축하는 설계 능력이 왜 중요한지 깊이 이해하게 되었다.

---

🔴 **문제 2: 파트 간 개발 규칙 부재로 인한 API 연동 예외 및 코드 파편화**

* **원인**: 백엔드 API URL 덤프 방식, DTO/Entity 분리 여부, CORS 정책, DB Naming Convention(스네이크 케이스 vs 카멜 케이스) 등에 대한 사전 협의가 부족하여, 코드 생성 및 프론트엔드 연동 시마다 직렬화 에러 및 DTO 매핑 예외가 발생함.
* **해결**: AI 코드 생성 및 팀원 공통 개발 표준을 강제하는 **`AI_RULES.md`** 명세서 작성. Controller-Service-Repository-DTO 엄격한 계층 분리, Swagger 자동 문서화, JPA Entity 명명 규칙, CORS 글로벌 설정 규칙을 명시하여 코드 품질 향상 및 파편화 방지.
* **느낀점**: AI 툴을 활용하거나 타 파트와 협업할 때 명확한 '컨벤션(Convention)'을 정해두지 않으면 코드 리뷰 및 통합 테스트 단계에서 불필요한 리팩토링 시간이 기하급수적으로 늘어난다. 규격화된 Rules 문서를 프로젝트에 탑재함으로써 코드 일관성을 유지하고 연동 에러를 사전 차단하는 노하우를 얻었다.

---

🔴 **문제 3: 파트 간 작업 의존성(Dependency)으로 인한 일정 지연 및 통합(Integration) 에러**

* **원인**: "프론트엔드 화면 구현"과 "백엔드 API 개발", "DB 스키마 구성"의 순서와 데이터 주고받는 시점이 불명확하여 상대방의 작업이 끝날 때까지 대기하거나, 중간발표/최종 통합 시점에 한꺼번에 연동을 시도하다가 에러가 대량 발생하는 구조적 한계 존재.
* **해결**: 각 주차별 파트별 세부 역할과 파트 간 데이터 의존 관계(예: 프론트엔드 AI 추천 렌더링을 위해 백엔드 2주차 `/api/recommendations` API 선행 필요 등)를 정리한 **`TASKS.md`** 마일스톤 구축.
* **느낀점**: 백엔드 개발자는 자신의 API만 만들고 끝나는 것이 아니라, DB 팀원의 스키마 제공 시점과 프론트엔드 팀원의 API 소비 시점을 고려한 **'스케줄링 및 의존성 관리'**를 할 수 있어야 프로젝트가 지연 없이 원활하게 굴러간다는 점을 체득했다.
