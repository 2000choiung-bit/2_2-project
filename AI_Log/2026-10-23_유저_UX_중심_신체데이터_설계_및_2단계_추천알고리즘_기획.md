# 📝 [Troubleshooting] 사용자 진입장벽 완화를 위한 신체 데이터 조건부 요구 및 2단계 핏 추천 알고리즘 설계

## 1. 개요 (Overview)

* **작업 내용**: 불필요한 인증 절차(이메일/문자 인증) 제거, 회원가입 진입장벽 완화를 위한 신체 데이터 필수/선택 조건 분리, 유저 입력 데이터 유무에 대응하는 백엔드 '2단계 사이즈 추천 알고리즘' 아키텍처 설계
* **관련 기술**: Java 17, Spring Boot 3.x, Spring Data JPA, Spring Security (BCrypt), Validation (`@Valid`)

---

## 2. 발생한 문제 및 해결 과정 (Trouble Shooting)

🔴 **문제 1: 상세 신체 수치(어깨너비, 가슴둘레 등) 강제 입력으로 인한 회원가입 진입장벽 및 유저 이탈율 우려**

* **원인**: 초기 기획 시 정확한 AI 피팅 추천을 위해 회원가입 시점에 키, 몸무게 외에도 어깨너비(`shoulder`), 가슴둘레(`chest`) 등 상세 치수 입력을 필수로 받으려고 함. 그러나 일반 사용자는 자신의 어깨너비나 가슴둘레를 정확히 알지 못하므로 가입 단계에서 귀찮음을 느껴 서비스를 이탈할 위험이 매우 높음.
* **해결**: 
  1. **필수값(Required)**: `username`, `password`, `name`, `height`(키), `weight`(몸무게)만 최소한으로 요구하여 진입 장벽 최소화.
  2. **선택값(Optional / Nullable)**: `shoulder`(어깨너비), `chest`(가슴둘레) 등은 `nullable = true`로 설정하여 원하는 유저만 자유롭게 수동 입력/수정할 수 있도록 자율성 부여.
* **느낀점**: 백엔드 개발자는 데이터 모델링 시 단순히 "많은 데이터를 확보하면 좋다"는 공급자 중심 사고에서 벗어나, 유저의 행동 패턴과 UX(사용자 경험)를 고려해 데이터 필드의 `Nullable` 여부를 전략적으로 결정해야 함을 배웠다.

---

🔴 **문제 2: 유저마다 입력된 신체 데이터 완성도가 다른 상황에서의 사이즈 추천 계산 예외 처리**

* **원인**: 어떤 유저는 키/몸무게만 입력하고, 어떤 유저는 어깨너비/가슴둘레까지 입력하여 DB에 저장된 유저 프로필 데이터의 파편화가 발생함. 하나의 계산 로직만 적용할 경우 `NullPointerException`이 터지거나 부정확한 추천 결과가 반환될 위험이 존재.
* **해결**: 백엔드 서비스 레이어(`SizeRecommendationService`)에서 **"2단계 추천 분기 알고리즘"** 구현.
  - **[Case A] 어깨/가슴 수치 존재 (`shoulder != null`)**: 유저가 수동 입력한 상세 스펙을 직접 반영하는 **"정밀 맞춤 추천 알고리즘"** 구동.
  - **[Case B] 키/몸무게만 존재 (`shoulder == null`)**: 백엔드 내부의 **"체형 표준 데이터 연산(키·몸무게 기반 평균 치수 추정) 알고리즘"**을 구동하여 추천 수행.
* **느낀점**: 입력 데이터의 완성도에 따라 백엔드 알고리즘을 유연하게 분기시킴으로써, 모든 유저에게 예외(Exception) 없이 안정적인 서비스를 제공하면서도 고도화된 추천 기능을 동시에 만족시킬 수 있는 구조적 유연성을 확보했다.

---

🔴 **문제 3: 상품 상세 페이지 접근 시 매번 신체 치수를 입력해야 하는 UX 번거로움**

* **원인**: 상품 추천 API 호출 시마다 프론트엔드에서 유저의 키/몸무게를 매번 Request Body로 전달받도록 설계할 경우, 보안상 취약하고 사용자 경험이 저하됨.
* **해결**: 
  1. **비밀번호 암호화**: `BCryptPasswordEncoder`를 적용하여 보안 강화.
  2. **유효성 검사**: `@Valid` 및 Service 단 로직을 통해 필수값(`height`, `weight`) 누락 검증 및 `username` 중복 체크.
  3. **자동 연동 흐름 구축**: 로그인 성공 시 부여된 인증 토큰(JWT/Session)을 기반으로, 사이즈 추천 API 호출 시 서버에서 유저 ID를 식별하여 DB(`member_profile`)에 저장된 프로필을 자동 조회 및 반영하도록 처리.
* **느낀점**: 클라이언트가 보내는 파라미터에 의존하지 않고, 백엔드 인증 체계 내에서 로그인된 유저의 프로필을 자동으로 가져와 로직을 돌리는 것이 현대적 RESTful API 설계의 기본이자 핵심임을 체득했다.
